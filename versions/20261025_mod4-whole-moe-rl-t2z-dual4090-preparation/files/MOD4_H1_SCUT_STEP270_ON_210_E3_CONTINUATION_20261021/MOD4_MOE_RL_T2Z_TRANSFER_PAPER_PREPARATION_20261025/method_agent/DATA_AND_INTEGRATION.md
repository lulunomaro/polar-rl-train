# Whole-stack data and executable upstream bridge

Contract schema: `mod4.moe.t2z.raw.v1`. Main modality: native RGB + **precommitted command/route plan**, with a shared environmentz. The source log also retains actual per-physics target6, actual expert activation/routing weights, dispatch/inference clocks and native outcome truth. Those latter fields are audit/diagnostic data and never automatically become prospective candidate features.

## Required source registry and clocks

Record each expert and gate's actual SHA, source/config/qualification receipt and pool-version SHA. Current player source identities are E0 `b10958...`, W35 `b026ad...`, gate148 `02718c...`, H1pair47 `4fb8e4...`, E2cohort52 `67895d...`, E3pair47 `2e3362...`; full hashes and manifest bytes/hash are in `source_facts.json`. New H1/E3source67 references are separately labeled root-provided training provenance, not current player source. No policy weights were opened here.

Use integer physics tick and absolute simulation nanoseconds, separately from100Hz dispatch tick, expert inference tick and wall-clock/camera exposure time. Main PhysX dt=2.5ms gives4physics ticks per100Hz dispatcher and8per50Hz expert period. Player MuJoCo dt=0.5ms gives20and40respectively. At20fps each frame spans20PhysX or100MuJoCo physics intervals. E2/E3periods cross video boundaries at2.5periods/frame; never round to2or3commands/frame. Preserve actual held output and mode-entry immediate-inference/reset-phase behavior from the collector, not a guessed permanent clock phase.

The current player clock source resets phase on mode change and holds E2/E3output for two outer ticks; this is logged source behavior, not a promise the future PhysX MoE collector has already implemented an identical lifecycle. Main collection must record its actual scheduler state/clock receipts and explicitly version any difference.

## Episode fields and semantics

Top-level `backend` includes name, physics_dt_ns,20fps video period,100Hz dispatcher period and expert_period_ns map. The schema rejects clock/backend mismatch. `expert_pool` records all five expert identities; the gate/cohort/controller contract must also be indexed by the real collector. Synthetic test hashes are deliberate placeholders.

Each episode has global source_episode_uuid, fragment episode_id, stable physical_config_id, collector/source/config SHA, task tags, reset/change times, native frame references, applied_steps, policy_events, a causal proposal and evaluation_only sidecar. Actual physical factors are private splitter/scorer metadata, not features. Geometry/controller/cohort/task/backend are separately indexed; physical grouping is based on actual fixed configuration receipts, never vector slot or requested seed alone. Same physical group across different expert tasks sharesz.

`applied_steps` covers every backend physics interval exactly and records six actually applied targets in `[left_crank,left_hip,right_crank,right_hip,left_wheel_spin,right_wheel_spin]`, units `[rad,rad,rad,rad,rad/s,rad/s]`. Sampled/clipped/requested/queued/applied/torque stages remain distinct audit fields. `expert` identifies the action source; `gate_weights5` needs an explicit collector semantics receipt. In the current hard whole-action stack a5vector can be the executed route onehot; it is not evidence of a new learned five-way gate or weighted action averaging. Preserve original two-way gate scores separately when available; do not invent unlogged soft weights.

`policy_events` covers each100Hz dispatcher boundary, with selected expert, actual latest inference tick per expert (null if not evaluated), commanded twist/height channels and gate invocation/hold/reset receipts. The lightweight validator checks coverage, finite values and no future inference receipt. It does not independently attest actual inference count/phase or reconstruct missing scheduler state; a native collector receipt is still necessary.

`proposal` is a future command4+route schedule committed at/before the initial decision tick with semantics `PRECOMMITTED_COMMAND_ROUTE`. Command4is a versioned high-level plan vector (proposed vx,vy,yaw-rate,height); the actual collector must map it to the original command interface and freeze that mapping. It is not the expert observation vector or target6. Training/query outcomes must come from executing this plan. Unknown future closed-loop gate output cannot be copied into it. Delayed commands remain command-conditioned; future applied timing stays private.

At T=41 the command/route tensor is `[1,41,M,10]`:9features and validity; M=20or100depending onbackend. The applied diagnostic tensor is `[1,41,M,17]`:target6+expertonehot5+routingweights5+validity. Item0is a zero/mask0anchor; every later frame contains the ordered physics intervals ending at that frame. No averaging,14Dpadding, missing-frame repetition or reset concatenation occurs. A different feature/backend schema requires new adapter weights/statistics.

The current validation code allows5-frame synthetic geometry only to keep CPU tests small; real checking requires41native frames. It rejects synthetic on the default real path, missing episodes, bad origins, clock/coverage/reset/split errors and late/missing proposal. `local_native_decoder` additionally checks local path containment, existence, SHA and RGB image decode. Collector provenance/contact identity/camera latency and actual file geometry still need an independent full receipt. No output is claimed training-ready.

## Data separation

Train/val/test split by physical config before clips/stats. A source episode cannot appear in two roles, and held-out supports and queries are distinct episodes in the same group. `SafeMoEIndex.train_metadata()` exports **only train/fit**, gives opaque contiguous context_index values, and never writes a fake friction value. `MoETrainingDataset` only enumerates those rows. Support/query views are requested independently; query gets only initial RGB and committed plan. It gets no futureRGB, actualfutureaction/gate, physicalfactor/contact/state/reward/success or train latent index.

The model process must not mount the combined private manifest/evaluator sidecar. Export fit/support/query views into separate namespaces and keep native future/contact truth in a scorer-only namespace. The code's allowlist and counterfactual tests are not operating-system access control. URI/sample IDs are loader bookkeeping, never text/prompt tokens. A native-data deployment audit must verify actual mounts and downstream tensor construction. Test latent adaptation uses observed completed support only; no nearest-factor/training-table lookup or query-driven early stopping.

## Executable fixed upstream binding

Fixed source is `c72f051f5cffcb1f372a32bc488df273556d39b9`. Small exact source snapshots/receipts are retained in the earlier integration_v1 history and indexed here by path/hash. No GitHub API, model/data download or upstream full package import was used for these tests.

`moe_train_entry.py` does not invoke `t2z/train.py` because its original metadata path overwrites selected rows to train and uses task-specific friction grouping. Instead it validates the whole-stack manifest and constructs `SafeMoEIndex`. Optional `--cpu-import-upstream <installed-checkout>` first verifies four fixed source hashes, imports `t2z.training.ours`, `scripts.train` and the action pipeline, and installs `bind_ours`; it never calls main or a model constructor. That full-import option is **not run here**; root can run it later in72's independent installed environment.

`bind_ours` installs actual callable replacements into those imported modules:

1. `ours._read_jsonl`, `_unique_friction_values`, `_metadata_index`, `build_dataset` accept only the bound `moe://train-fit` handle and train-only in-memory rows. Legacy function/table names are retained only for upstream call compatibility; values are ordinal context_index, never actual friction. Val/test metadata cannot be accepted as that train handle.
2. `GroupedContextStage1Module.get_pipeline_inputs` looks up the ordinal context table or accepts an explicitly supplied direct context for a future support-z path; then calls the actual base `scripts.train.WanTrainingModule` input method. Physical-factor keys are rejected and routing IDs are removed from neural inputs.
3. The factory in `scripts.train`, used by `WanTrainingModule.__init__`, is wrapped. It calls the original factory with `ckpt_path=None`, installs a new MoETemporalActionEncoder using D read from the original encoder, then optionally applies an explicitly provided pretrained reader through a filter that skips every action_encoder key. Old14D action tensors never load into the new layer. Report all skipped/DIT/context missing/unexpected keys; an unreviewed extra checkpoint branch rejects. The adapter's own resume demands strict matching and rejects old action_mlp/action_embedding keys.
4. Upstream WanVideoUnit_ActionEmbedder receives the dense4Dtensor and calls the new `encode_ti2v2`, producing context `[B,41,D]` and modulation `[B,11,D]`. Three zero anchors preserve original causal VAE grouping; one future group covers four video intervals, with all backend intervals represented.
5. `runner.main` is replaced by a training-disabled guard. A named original-main reference is retained only for a future separately reviewed launcher and CPU AST stub tests, not exposed as an enabled CLI. The preparation artifact has no train-enable flag. Legacy friction curriculum, structured sampler and old context-table resume paths reject until explicitly ported/audited; the original baseline config cannot silently run them.

The code does not modify an installed upstream checkout or the production PPO. All monkeypatches are local to the isolated imported process. For an actual future training launch, a reviewed runner must bind the safe loader/factory before model/optimizer construction, use a real native decoder and train-only statistics, define new context-index checkpoint serialization/resume, and explicitly authorize a finite stage. The current main guard must remain until that future concrete stage is approved; data check is not approval.

## What the CPU evidence establishes

The tests execute the exact fixed source AST bodies of WanVideoUnit_ActionEmbedder.process and base training input methods with tiny CPU tensors/stub images. A separate test executes the exact fixed `ours.main` call body with fake parser/Accelerator/model/logger/launch objects. It follows the real main→build_dataset→module/factory→base inputs→action unit path and ends at `[1,11,24]`; no actual Accelerator, Wan weights, denoiser, VAE, policy, simulator or training loop runs. Both PhysX20tick andMuJoCo100tick action-unit paths were tested. D24is a synthetic stub width, not a measured Wan configuration.

These tests establish executable Python symbol/shape/data-routing compatibility at the checked boundaries. They do not prove full installed dependency imports, VAE/DiT spatial/temporal integration, flow loss, z adaptation, checkpoint correctness on real weights, convergence, memory fit or performance. Those remain named pending items. Re-run later checks under new unique IDs; retain failures and originalsource snapshots. Never relabel local CPU results as host72 or native physics results.
